# OpenAI Agent Analysis Module Boundaries

## Goal

Replace the container-local AI CLI subprocess with direct, stateless OpenAI Responses API execution while preserving API-owned analysis lifecycle semantics and adding a provider-neutral Telegram experience for one-shot report and deep-research runs.

## Non-Goals

- Add conversational follow-ups, conversation history, or provider-owned durable state.
- Add Web or MCP user experiences for report or deep research.
- Support multiple generation dialects such as Chat Completions alongside Responses.
- Allow users, Telegram chats, channel accounts, or individual runs to select provider endpoints or credentials.
- Preserve Claude Code, Codex CLI, Node-based AI tooling, local shell execution, local file-editing tools, or arbitrary MCP tools in the agent-runner container.
- Change CopperASR, transcription planning, transcript reuse, collection membership, export jobs, or media ingestion ownership.
- Define the final Telegram copy/layout, result JSON schema, model default, retry schedule, or implementation sequence. Those are internal design decisions for the bound modules.

## Constraints And Assumptions

- Source-context SHA-256: `aebd86b6eab2887f2e4788c8a4148b84a360a742432a9bfca8758cc8954c871d`.
- The current checkout runs `claude --print` through `subprocess.run`; it does not contain an active or historical `codex exec` path. The removal boundary therefore covers the complete CLI/subprocess harness, its Claude-specific settings, its Node/CLI image dependency, and its active tests and documentation.
- The OpenAI Responses API is the only generation protocol in scope. A deployment may configure a different base URL only when that endpoint conforms to the required Responses contract.
- Endpoint, API credential, model, timeout, and related provider settings are deployment configuration supplied through environment variables or secret-file references. They are not product state and do not belong in `analysis_run`, channel-account, or Telegram state.
- Requests are one-shot and use `store: false`. Durable lifecycle, idempotency, cancellation, lineage, artifacts, diagnostics, and recovery remain owned by the platform API.
- `store: false` disables provider-side durable Response application state; it is not treated as a zero-retention guarantee. Before configuring an endpoint, the deployment owner must accept that provider's data-processing, retention, residency, and abuse-monitoring policy.
- Protocol conformance is not sufficient to trust an endpoint. AI Execution Runtime binds credentials to the deployment-approved endpoint origin, fails closed on cross-origin redirects instead of forwarding authorization, and sends only content authorized by the normalized execution request. Provider-side search queries are an additional external disclosure allowed only for `deep_research`.
- `report` may use only the user's declared transcript or text-corpus inputs. `deep_research` may additionally use provider-side web search and must return source evidence suitable for persisted artifact lineage and user-visible citations.
- The agent runner never reads raw speech inputs. It receives only API-declared, prepared transcript or text-corpus artifacts and safe metadata.
- Telegram, Web, and MCP remain thin adapters. Only the Telegram adapter changes in this initiative.
- Provider secrets, complete prompts, private source text, provider reasoning, and unsanitized response bodies must not appear in ordinary logs or public diagnostics.
- Existing API lifecycle and worker verification gates remain load-bearing: declared inputs, prerequisite planning, cooperative cancellation, terminal-state fencing, artifact publication, diagnostics, idempotency, result deduplication, and restart recovery.
- Exact environment names, normalized execution schema, output artifact schema, retry/backoff values, cancellation transport, Telegram gestures/copy, and result presentation remain open module-internal decisions. They do not alter the responsibility map below.

## Boundary Changes

- 2026-08-03: Initial approved map. Split provider execution, API-owned product orchestration, and Telegram presentation because each has an independently verifiable outcome, a distinct state/trust boundary, and an honest substitute at every connection.
- 2026-08-03: Kept report and deep-research execution in one AI runtime module because they share one provider protocol and lifecycle; their only boundary-relevant difference is the approved tool policy.
- 2026-08-03: Excluded conversation state, Web/MCP UX, provider selection per run, alternate API dialects, and local execution tools from the initiative.
- 2026-08-03: Added the external Responses provider trust boundary after security review. Clarified that deployment approves provider data handling, runtime binds credentials and authorized content to that origin, provider-side search disclosure is deep-research-only, and `store: false` is not a zero-retention guarantee.
